# ARTHA

**AI-Powered Hyper-Personalised Banking for Bharat**
A suitability-first lending intelligence layer for Indian banking.

> We do not maximise how much a customer borrows.
> We maximise the probability that they keep paying.

Team Wowwsters · Theme — Digital Transformation in Lending

---

## What this is

An implementation of the ARTHA design described in `ARTHA_Report.pdf`: a
decision-and-delivery layer that sits *beside* a bank's core banking system,
consumes transactions through change-data-capture, decides inside the bank's own
environment, and renders those decisions back into the bank's existing channels.
No change to core banking is required.

The governing design rule is that **the language model is the mouth, not the
brain.** Decisions are produced by an auditable pipeline of deterministic rules,
cash-flow simulation and tabular models that emit reason codes. The language
model only renders a completed decision into natural speech.

Six things make it different from a conventional recommender, and all six are
mechanisms in this repository rather than claims in a document:

| | Mechanism | Where |
|---|---|---|
| 1 | **The Financial Twin** — a Monte-Carlo simulation of the next six months of balance, run *before* any product is shown, stress-tested, and returning a counterfactual rather than a refusal | `backend/artha/engines/twin.py` |
| 2 | **A constraint layer that can refuse** — the Suitability Gate overrides the ranking, sizes products to Twin-safe exposure, and reports its own suppressions as a success metric | `backend/artha/gate/suitability_gate.py` |
| 3 | **The Intervention Ladder** — grades interventions by *regulatory* as well as economic cost, and leads with the EMI date shift | `backend/artha/intervention/ladder.py` |
| 4 | **Portfolio-level correlated detection** — 340 borrowers sharing an employer is one payroll delay, not 340 events | `backend/artha/engines/sentinel.py` |
| 5 | **Containment of the language model** — narrations are parsed to typed values, every numeral is grounded, and action requires a signed single-use token plus explicit confirmation | `backend/artha/llm/` |
| 6 | **The dual-rendering Decision Object** — one artefact rendered as a regulator trace and as one spoken sentence, so they cannot diverge | `backend/artha/core/decision.py` |

## Status, honestly

This is at **concept and prototype stage**, matching §11 of the report.

* No integration with a live bank, no production Account Aggregator connection,
  no live bureau pull.
* **Every rupee amount, probability, count and performance figure produced by
  this system is illustrative**, generated by the synthetic transaction
  generator in `backend/artha/synth/generator.py`. Nothing here is a measured
  portfolio result. The UI labels this on every screen that renders a number.
* Regulatory framings (Special Mention Account classification, the treatment of
  restructuring granted for borrower financial difficulty, Key Fact Statement
  format, cooling-off periods, data localisation, DPDP) are used as **design
  hypotheses flagged for verification against current RBI and MeitY circulars**
  before submission or presentation. See `docs/CLAIMS_REGISTER.md`.
* Language coverage is an **integration claim, not a modelling claim**. The
  Bhashini/AI4Bharat adapters are real interfaces with a stub provider that
  deliberately does not fake translation.

### What has actually been executed

| Component | Verified? |
|---|---|
| Engine (ontology, Twin, Gate, Sentinel, ladder, firewall, journey, KFS) | **Yes** — 143 pytest tests pass |
| Synthetic generator and income typing across 11 archetypes | **Yes** |
| React console / customer app | **Syntax-checked only** (25/25 files); not built or run |
| FastAPI service | **Never started.** 12 route tests written in `tests/test_api.py`, skipped without fastapi |
| Persistence (`artha/db`) | **Not wired.** Schema written; nothing writes through it |

The development machine had no working Python or Node toolchain, so the test
suite was executed under **Pyodide** (CPython 3.14 + numpy, compiled to
WebAssembly, in a browser) via `tools/mkpytest.sh`. That is a real interpreter
running the real suite, but the API and front-end layers have not been run
end-to-end. Do that first (see below) before demonstrating.

## Quickstart

### Backend

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env
pytest -q                       # 143 tests + 12 API tests that need fastapi
uvicorn artha.main:app --reload # http://127.0.0.1:8000/docs
```

The service seeds all eleven synthetic archetypes on first request, so the
console has data immediately.

### Banker console

```bash
cd console && npm install && npm run dev     # http://localhost:5173
```

### Customer app

```bash
cd customer-app && npm install && npm run dev # http://localhost:5174
```

Both proxy `/api` to `http://127.0.0.1:8000`, so start the backend first.

## Testing

```bash
cd backend && pytest -q
```

The suite asserts behavioural promises, not only that the code runs — that a
customer in stress is never sold to, that the ladder leads with the zero-cost
rung, that a revoked consent purpose stops a recommendation at inference time,
that hallucinated numbers are blocked, that declining an offer is not recorded
as a risk signal, and that the audit chain detects tampering.

### Running without a toolchain

`tools/` contains the offline harnesses used to build this on a machine with no
interpreter:

```bash
export ARTHA_DOCROOT=/some/served/directory
tools/mkpytest.sh "tests -q"     # runs pytest under Pyodide in a browser
tools/mkfrontcheck.sh            # transpiles every .ts/.tsx to catch syntax errors
perl tools/serve.pl 8787 "$ARTHA_DOCROOT"
```

These are development aids, not part of the product.
